# Stripe sandbox integration

The Stripe planner recommended hosted Checkout Sessions for the site's one-time web orders and the Stripe Dashboard's hosted Invoice Page for occasional manual invoices. No Stripe integration existed before this sandbox implementation.

The integration supports **local test mode** and a separately gated **production live mode**. A live checkout is not shown merely because the code is deployed: the production key, webhook secret, and explicit live switch must all be set on the production host. Retain Stripe's written catalog approval with your merchant records.

## Local setup

1. Use a test-mode API key from the **same Stripe account** as the webhook listener. An existing key is sufficient; a new key is not required. Prefer a restricted test key with permission to create and read Checkout Sessions. Keep credentials in a secrets vault or, for local development, the gitignored `.env`; never paste them into chat or commit them. Set `STRIPE_TEST_SECRET_KEY` to a `sk_test_` or appropriately restricted `rk_test_` key, `STRIPE_TEST_WEBHOOK_SECRET` to a `whsec_` signing secret, and `STRIPE_SANDBOX_CHECKOUT_ENABLED=true`. Use `NODE_ENV=development` (or leave it unset).
2. For local webhook forwarding, install the official Stripe CLI and log in to the **same test account**. Run `stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded --forward-to http://localhost:3000/api/stripe/webhook`. Copy the listener's `whsec_` signing secret into the local `.env` as `STRIPE_TEST_WEBHOOK_SECRET`, then start/restart the app with `npm start` while keeping the listener running. Stripe's current CLI docs say the listener signing secret stays the same across restarts of `stripe listen`; recheck it if you change CLI login context. Do not register `https://highlandpeptides.com/api/stripe/webhook` in the Dashboard: this route deliberately returns 404 on Render/production. Only create a Dashboard test webhook after a reachable, separately hosted test endpoint exists, and use that destination's own signing secret.
3. Verify the checkout email, enter a complete address and select **Card (Stripe test mode)**. Complete a payment with a [Stripe test card](https://docs.stripe.com/testing). In test mode, the redirect page explicitly says webhook confirmation may still be pending. Confirm the exact order amount and order status in the local admin panel. Try cancellation, decline, wrong webhook signature, and duplicate webhook delivery.
4. For occasional invoices, use the sandbox Dashboard to create a customer and invoice with an accurate description of the actual goods, enable the hosted invoice page, and send a test invoice. These manually created invoices are **not** mapped to storefront orders; do not mark a local order paid merely because an unrelated Stripe invoice is paid.

The server recomputes cart prices and discounts, validates the research declaration, verifies email/address, saves a pending order, and creates a hosted Checkout Session. The session itemizes the saved products (including free rewards), allocates the saved discount and store credit across merchandise, adds shipping and fees, and refuses to start if the line-item sum differs from the saved order total. The webhook checks its signature, active mode, order/session IDs, currency, and amount before marking the order paid. Duplicate and late events do not pay a cancelled order. The redirect alone never marks it paid.

## Live launch

1. Keep the live key and webhook signing secret in your host's secret settings, **not** in `.env`, source control, chat, or frontend code. Prefer a restricted live key (`rk_live_`) with only the permissions needed to create Checkout Sessions. Set `STRIPE_LIVE_SECRET_KEY` and `STRIPE_LIVE_WEBHOOK_SECRET`. They must belong to the same live Stripe account. Do not reuse the Stripe CLI listener secret: Dashboard webhook destinations have separate signing secrets.
2. Deploy this code to the production host. In the **live** Stripe Dashboard, create a webhook destination at `https://highlandpeptides.com/api/stripe/webhook` for `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Copy that destination's signing secret into the host's secret settings. Ensure the production order database is persisted across deploys and restarts.
3. Set `STRIPE_LIVE_CHECKOUT_ENABLED=true` and restart/redeploy. Check `https://highlandpeptides.com/api/stripe/config`: it must return `{"enabled":true,"mode":"live"}`. If a key or signing secret is missing, the card option stays hidden. Do not place a real customer order to diagnose configuration.
4. Run a controlled low-value **real** order only after the host and webhook are confirmed. Verify the charged amount and SKU description in Stripe, the matching Highland order number, one signed webhook delivery, and the order moving from `pending_payment` to `paid` exactly once. Cancel/refund that charge in the Dashboard if appropriate; account for Stripe's refund fees. The browser return page by itself is not proof of payment.
5. Stripe Dashboard invoices are separate from the storefront and do not automatically reconcile to Highland order numbers. Handle refunds, disputes, and asynchronous failures in the Dashboard until a separate synchronization workflow is built.

Keep catalog descriptions and laboratory reports accurate; do not treat a payment-provider approval as a verification of scientific claims or a substitute for applicable legal review.
